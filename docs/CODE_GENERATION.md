# Code Generation Script

## What it is

`scripts/generate_foundation.py` created the initial multi-module foundation (POMs, packages, placeholders, Compose, config-repo, docs stubs).

It is a **bootstrap tool**, not an ongoing code generator for feature work.

## Danger

Running it again will **overwrite** many files with template output, including:

- service `application.yml` / Java placeholders
- root `README.md` / some docs generated by the script
- Docker Compose fragments it owns
- config-repo entries it regenerates

Hand-fixes made after the first generation can disappear.

## When it is OK to re-run

- Greenfield reset of the foundation (you accept full overwrite)
- Reproducing the skeleton in an empty directory
- You have committed / branched and can diff/revert

## When not to re-run

- After you have real business logic, migrations, or hand-tuned config
- Just to add one service — use [ADDING_A_SERVICE.md](./ADDING_A_SERVICE.md) instead (copy an existing module)

## Safer workflow after foundation day

1. Treat generated services as source of truth in git
2. Add services by copy/adapt
3. Keep docs updated manually (this `docs/` folder)
4. If you must change the generator, update the script **and** apply the same change to live modules (or generate into a temp dir and cherry-pick)

## Post-generation fixes that were applied (do not regress)

These bit us; keep them:

1. Rename Eureka custom config away from `EurekaServerConfig`
2. Feign interceptor bean ≠ `correlationIdInterceptor`
3. Gateway depends on `spring-cloud-starter-loadbalancer`
4. Eureka `registry-fetch-interval-seconds: 5` on clients/gateway
5. Gateway rewrite routes (not only discovery locator)
6. Java 21 required for Lombok
7. Kafka/Redis gated in `dev` for reliable local boot
